## Фазы реализации

### Фаза 1: Ключ партиции order_uuid (Tracer Bullet)

**Цель:** События одного заказа попадают в одну партицию и приходят по порядку.
**Затрагивает:** backend (`order`, `assembly`)
**Задачи:**

- [x] Тест: producer `order.paid` отправляет сообщение с ключом `order_uuid`
- [x] Использовать `order_uuid` ключом в `order/internal/service/producer/order_paid_producer.go`
- [x] Тест и замена ключа в producer `ship.assembled` в `assembly`
- [x] Обновить `docs/architecture.md`: п. 8 перенести в решённые

**Когда готова:** тесты проверяют ключ в обоих producer; `task test` зелёный.

### Фаза 2: Условный UpdateOrderStatus

**Цель:** Устаревшее или повторное событие не откатывает статус заказа.
**Затрагивает:** backend, database (`order`)
**Задачи:**

- [x] Тесты допустимых и недопустимых переходов для всех пар статусов
- [x] Условное обновление в репозитории (`UPDATE ... WHERE status IN (допустимые)`)
- [x] Использовать его в `UpdateOrderStatus` и в consumer `ship.assembled`
- [ ] Интеграционный тест на postgres: `ASSEMBLED` не откатывается в `PAID` (переходы покрыты unit-тестами сервиса; на реальной БД не проверено)

**Когда готова:** переход `ASSEMBLED` -> `PAID` не меняет заказ; повтор `ASSEMBLED` -> `ASSEMBLED` не ошибка.

### Фаза 3: Повторы и DLQ у consumer

**Цель:** Сообщение не теряется молча: оно либо обработано, либо лежит в `<topic>.dlq`.
**Затрагивает:** backend (`platform/pkg/kafka`, конфиги сервисов)
**Задачи:**

- [x] Тесты: 3 вызова с задержками 1/2/4 с; успех на 2-й попытке не создаёт DLQ-запись
- [x] Повторы с экспоненциальным backoff в `group_handler.go`, настройка через конфиг
- [x] Отправка в `<topic>.dlq` с заголовками исходных topic/partition/offset и ошибки
- [x] Offset не помечается, если не удалась и отправка в DLQ; тест
- [x] Подключение DLQ для `assembly`, `order`, `notification` (топики `<топик>.dlq` создаются автоматически: в Kafka включён `KAFKA_AUTO_CREATE_TOPICS_ENABLE`)

**Когда готова:** тест с падающим handler оставляет сообщение в DLQ и обрабатывает следующее.

### Фаза 4: Дедупликация по event_uuid

**Цель:** Повторная доставка не вызывает двойную сборку и повторное обновление заказа.
**Затрагивает:** backend (`assembly`, `order`, `platform/pkg/cache`)
**Задачи:**

- [x] Тесты: дубликат `order.paid` не запускает сборку, дубликат `ship.assembled` не обновляет заказ
- [x] Middleware дедупликации на Redis с TTL 24 ч (настраивается)
- [x] Подключить в `assembly` и `order`; определить и описать поведение при недоступности Redis
- [x] Тест недоступности Redis по принятому решению
- [x] Интеграционный тест (testcontainers) на реальном Redis: повторная доставка не вызывает обработчик второй раз (сквозной тест с Kafka не писался)

**Когда готова:** второй `order.paid` с тем же `event_uuid` не публикует второй `ship.assembled`.
