# Plan: Envoy вместо самописного BFF

**PRD:** [prd-replace-bff-with-envoy.md](prd-replace-bff-with-envoy.md)
**Дата:** 2026-11-08

## Фазы реализации

### Фаза 1: Envoy рядом с BFF, вход и `me` через transcoder (Tracer Bullet) — выполнена

**Цель:** Доказать весь путь на минимальном срезе: браузерный запрос превращается Envoy в gRPC-вызов `iam`, сессия доходит до сервиса. BFF и фронтенд не трогаем, система работает как раньше.
**Затрагивает:** backend
**Задачи:**

- [x] Аннотации `google.api.http` для `Login` и `Whoami` в `backend/shared/proto/iam` с прежними путями `/api/auth/login` и `/api/auth/me`; перегенерация (`task proto:gen`), `task proto:lint` проходит
- [x] Сборка дескриптора proto для Envoy (`task proto:descriptor`, файл `deploy/compose/envoy/proto.pb` не хранится в git)
- [x] Сервис Envoy в `deploy/compose/envoy` с конфигурацией transcoder для `iam`, передачей сессии заголовком `Session-Uuid` и healthcheck; запускается в `task up-all` на порту `:8085`, BFF остаётся на `:8095`
- [x] Smoke-тест `task envoy:test`: `POST /api/auth/login` -> `GET /api/auth/me` через Envoy возвращают те же данные, что BFF (в формате proto-JSON), плюс ошибки `401` и `400` с полем `message`
- [x] Unit-тесты и `go vet` проходят для Go-модулей после перегенерации proto

**Когда готова:** после `task up-all` вход и `GET /api/auth/me` по сессии через Envoy возвращают данные пользователя, healthcheck Envoy зелёный, фронтенд по-прежнему работает через BFF.

**Что выяснилось по ходу:**

- `Whoami` в `iam` брал сессию только из поля запроса `session_uuid`, а transcoder кладёт заголовок в gRPC-metadata. Добавлен обратно совместимый запасной путь: если поле пустое, сессия берётся из metadata `session-uuid` (тест `backend/iam/internal/api/auth/v1/api_test.go`). Остальные сервисы уже читают сессию из metadata.
- Заголовок сессии для Envoy называется `Session-Uuid` (в BFF был `X-Session-Uuid`): он попадает в metadata без переписывания. Фронтенд перейдёт на него в фазе 3.
- Transcoder пересчитывает маршрут после переписывания пути, поэтому маршруты Envoy заданы по gRPC-сервису (`/iam.v1.AuthService/`), а не по REST-пути.
- `task proto:gen` был сломан после переноса сервисов в `backend/`: пути плагинов в `buf.gen.yaml` вели в несуществующий `backend/bin`, а Taskfile не ставил плагины `grpc-gateway`, `openapiv2` и `validate`. Исправлено. `buf generate` с `clean: true` стирает `backend/shared/pkg`, поэтому после него нужно вернуть `pkg/openapi` (результат `ogen`) и `pkg/swagger.swagger.json`.
- Локальный `golangci-lint` v2.1.5 не работает с Go 1.27.3 (ошибка export data, `typecheck` падает и на чистом `HEAD`), поэтому локально проверены `gofumpt`, `gci` и `go vet`; линт остаётся за CI.

### Фаза 2: Остальные маршруты и политики Envoy — выполнена

**Цель:** Envoy умеет всё, что умел BFF, плюс маршрутизацию `order`, CORS и корректный адрес клиента. Фронтенд всё ещё не переключён.
**Затрагивает:** backend
**Задачи:**

- [x] Аннотации `Register` (`iam`, `/api/auth/register`) и `ListParts` (`inventory`, `/api/parts`; пустой фильтр ведёт себя как в BFF); перегенерация proto
- [x] Маршрут `/api/v1` в `order` по HTTP и CORS для origin `http://localhost:5173` (методы, `Content-Type`, заголовок сессии)
- [x] Передача реального адреса клиента в `x-forwarded-for`; заголовок, присланный клиентом, не принимается на веру
- [x] Тесты в `task envoy:test`: `register`, `parts`, создание/оплата/отмена заказа через `/api/v1`, статусы `400`/`401`/`404`/`409` с полем `message`, preflight `OPTIONS`
- [x] Тест на ограничитель входа: шесть неверных входов с разными поддельными `X-Forwarded-For` блокируются, лимит считается по реальному адресу

**Когда готова:** все четыре эндпоинта и `/api/v1` через Envoy работают, preflight получает ответ с разрешениями, поддельный `X-Forwarded-For` не обходит ограничитель попыток входа.

**Что выяснилось по ходу:**

- `order` читает сессию из `X-Session-Uuid`, а iam и inventory получают её из заголовка `Session-Uuid` через transcoder. Чтобы фронтенд слал один заголовок, маршрут `/api/v1` копирует `Session-Uuid` в `X-Session-Uuid`; код `order` не менялся. CORS разрешает оба имени.
- Envoy при `use_remote_address` дописывает адрес клиента в конец `x-forwarded-for`, а ограничитель в `iam` берёт первое значение, поэтому присланный клиентом заголовок обходил лимит (проверено: 8 входов с разными поддельными адресами, ни одной блокировки). Заголовок на уровне virtual host перезаписывается реальным адресом соединения.
- CORS-фильтр ищет политику по исходному REST-пути, до переписывания transcoder'ом. Поэтому кроме маршрутов по gRPC-методу в конфигурации есть маршруты по REST-пути (`/api/auth/`, `/api/parts`, `OPTIONS /api/`). Наружу открыты только четыре метода (`Login`, `Whoami`, `Register`, `ListParts`), а не сервисы целиком.
- `Register` через Envoy отвечает `200`, BFF отвечал `201`. Фронтенд проверяет только успех, но в фазе 3 это стоит учесть. Тело регистрации вложенное: `{"info":{"user_info":{...},"password":"..."}}`.
- `GET /api/parts` без параметров возвращает все детали; фильтр передаётся как `?filter.category=CATEGORY_ENGINE`. Категория приходит именем enum, `int64` (`stock_quantity`) строкой.
- Лимит входа в `iam`: 5 попыток в минуту на адрес, считаются и успешные входы. Тест ограничителя идёт последним и исчерпывает лимит на минуту, а при повторном запуске скрипт сам ждёт окно.
- Отмена оплаченного заказа в `order` даёт `400` (`order already paid`), а не `409`.
- Существующий дефект `inventory`, не связанный с Envoy: первое обращение к Mongo после простоя падает на устаревшем соединении и висит до таймаута (воспроизводится прямым `grpcurl`). В smoke-тесте первый запрос каталога повторяется до трёх раз.
- Smoke-тест больше не использует `grpcurl`: пользователь создаётся через `/api/auth/register`.

### Фаза 3: Фронтенд переключается на Envoy — выполнена

**Цель:** Интерфейс ходит на единую точку входа и понимает формат proto-JSON.
**Затрагивает:** frontend
**Задачи:**

- [x] DTO и адаптеры `auth` под формат Envoy: вложенное тело регистрации, ответы `login` и `me` (`frontend/src/modules/auth/repository/`)
- [x] DTO и адаптер `catalog` под proto-JSON: `int64` строкой, вложенный производитель, enum категории (`frontend/src/modules/catalog/repository/`)
- [x] `vite.config.ts`: все `/api` проксируются на один адрес Envoy; обновить комментарии и `task frontend:dev`
- [x] Unit-тесты адаптеров и DTO на `int64`-строки и вложенные тела, обновить затронутые тесты (`auth-form`, каталог)
- [x] Тест обработки ошибок: тело `{"code","message","details"}` даёт сообщение пользователю, `401` приводит к выходу из сессии

**Когда готова:** регистрация, вход, каталог и заказы работают в браузере через Envoy, `task frontend:check` (типы, линтер, тесты) проходит.

**Что выяснилось по ходу:**

- Заголовок сессии во всех запросах фронтенда теперь `Session-Uuid` (`common/api/http.ts`); для `order` Envoy копирует его в `X-Session-Uuid`.
- `vite.config.ts` проксирует весь `/api` на Envoy (`http://localhost:8085`, переопределяется `API_PROXY_TARGET`). Проверено вживую через `:5173`: регистрация, вход, `me`, заказы. `task web` по-прежнему запускает и BFF, он уйдёт в фазе 5.
- Вход возвращает только `session_uuid`, `me` отдаёт вложенный `user.info`; в модуль `auth` добавлены `auth.dto.ts`, `auth.adapter.ts` и модель `Profile`. Каталог приходит в обёртке `{parts: [...]}`, `stock_quantity` строкой, производитель объектом; адаптер превращает остаток в число (нечисловое значение даёт 0).
- Модуль `system` всё ещё запрашивает `/api/health`, которого у Envoy нет, поэтому индикатор состояния показывает недоступность до фазы 4.
- Тесты: адаптеры `auth` и `catalog`, регистрация вложенным телом (`auth-form`), ошибка Envoy `{code,message,details}` и `401` -> выход из сессии (`query-client.test.ts`). `typecheck`, `lint --deny-warnings`, 130 тестов и `npm run build` проходят.
- Дефект `inventory` и Mongo (первый запрос каталога после простоя даёт `504`) проявляется и в браузере: первая загрузка каталога после паузы может занять 10 с и закончиться ошибкой, повторная работает сразу.

### Фаза 5: Удалить BFF — выполнена

**Цель:** Единственная точка входа — Envoy, самописного шлюза в репозитории нет.
**Затрагивает:** backend
**Задачи:**

- [x] Удалить каталог `bff/` и его запись в `go.work`, обновить `go.work.sum`
- [x] Удалить задачу `bff:run` из `Taskfile.yml`; `task web` запускает только фронтенд
- [x] Перевести порт Envoy на постоянное значение (освободившийся `:8095` или выбранное в фазе 1) и обновить переменные окружения и compose
- [x] Проверить, что нигде в Taskfile, compose и CI нет ссылок на `bff`
- [x] Прогнать `task lint`, `task test` и `task envoy:test`; CI на ветке зелёный

**Когда готова:** `grep -ri bff` по коду, конфигам и CI не находит ссылок, весь пользовательский путь работает через Envoy, CI зелёный.

**Что выяснилось по ходу:**

- Порт Envoy оставлен `:8085` (переменная `ENVOY_HTTP_PORT` в compose): он уже прописан в Vite, smoke-тесте и compose, а перенос на `:8095` ничего не даёт.
- `go.work.sum` не менялся: `bff` не добавлял в него записей. `go work sync` ничего не изменил.
- `task web` теперь вызывает только `frontend:dev`. В `.github/` ссылок на `bff` не было.
- `grep -riw bff` вне `docs/` пуст. В `docs/` остаются упоминания в PRD, плане и `docs/plan-iam-authentication.md`; последний уберём в фазе 6.
- Локально проверены `go build`, `go vet`, `task test` (без ошибок) и `task envoy:test`. `task lint` локально не гонялся (golangci-lint v2.1.5 не работает с Go 1.27.3, см. фазу 1), CI на ветке остаётся за вами.
