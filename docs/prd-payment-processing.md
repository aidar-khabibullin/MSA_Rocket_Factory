# PRD: Оплата заказа (payment)

**Дата**: 2026-11-08
**Статус**: Implemented

## Цель

Дать сервису заказов синхронный способ оплатить заказ и получить идентификатор транзакции, который затем попадает в уведомление пользователю.

## Пользовательские сценарии

- `order` отправляет заказ на оплату (`PayOrder`) -> получает UUID транзакции.
- Пользователь получает в Telegram способ оплаты и номер транзакции (через событие `order.paid`).

## В скоупе

- gRPC `PaymentService.PayOrder` (`backend/shared/proto/payment`, порт `:50052`), с HTTP-шлюзом (`backend/payment/internal/api/gateway`).
- Генерация UUID транзакции для каждого заказа; повторный `PayOrder` по тому же заказу возвращает ту же транзакцию.
- `RefundOrder`: возврат платежа (компенсация), идемпотентный по транзакции; после возврата заказ можно оплатить заново.
- Трассировка (`payment.process`), структурированный лог успешной оплаты.
- Health-check.

## Не в скоупе

- Реальная платёжная система: сервис имитирует оплату и всегда успешен.
- Хранение платежей и истории транзакций.
- Постоянное хранение платежей: записи лежат в памяти процесса, идемпотентность действует, пока сервис не перезапущен.

## Технические ограничения

- Сервис без состояния и без хранилища.
- Идемпотентность по `order_uuid` и возврат (`RefundOrder`) реализованы; записи платежей хранятся в памяти (`architecture.md`, пп. 2 и 5).

## Критерии готовности

- [x] `PayOrder` возвращает непустой UUID транзакции.
- [x] В спан и лог попадают `order_uuid`, `user_uuid`, способ оплаты и `transaction_uuid`.
- [x] Unit-тесты сервиса и API.
- [x] Идемпотентный ключ: повторный вызов с тем же ключом возвращает ту же транзакцию.
- [x] Метод возврата платежа для компенсации.
