# PRD: Надёжная доставка событий Kafka

**Дата**: 2026-11-08
**Статус**: Draft

## Цель

Исключить потерю, дублирование и переупорядочивание событий `order.paid` и `ship.assembled` между сервисами `order`, `assembly` и `notification`, чтобы оплаченный заказ гарантированно доходил до статуса `ASSEMBLED` ровно один раз.

## Пользовательские сценарии

- Клиент оплачивает заказ, а обработчик события в `assembly` временно падает -> сообщение повторяется, ракета собирается, заказ получает `ASSEMBLED`.
- Сообщение не обрабатывается после всех повторов -> оно попадает в DLQ, а следующие сообщения партиции обрабатываются без блокировки.
- Kafka повторно доставляет `order.paid` -> ракета не собирается второй раз и второй `ship.assembled` не публикуется.
- Событие `ship.assembled` приходит повторно или с опозданием -> статус заказа не откатывается и не перезаписывается.
- По одному заказу публикуется несколько событий -> consumer получает их в порядке публикации.
- Оператор разбирает проблемные сообщения -> он видит их в топике `<topic>.dlq` вместе с причиной ошибки.

## В скоупе

1. Ключ сообщения Kafka для событий заказа равен `order_uuid` вместо случайного `event_uuid` (producer `order.paid` в `order` и producer `ship.assembled` в `assembly`).
2. Consumer: ограниченное число повторов обработки с экспоненциальным backoff; offset сдвигается только после успешной обработки или после отправки в DLQ.
3. DLQ: топик `<исходный топик>.dlq` для каждого потребляемого топика; в сообщение добавляются исходный topic/partition/offset и текст последней ошибки.
4. Дедупликация по `event_uuid` в потребителях, которые меняют состояние: `assembly` (`order.paid`) и `order` (`ship.assembled`).
5. Условное обновление статуса в `UpdateOrderStatus`: статус меняется только если переход допустим из текущего статуса.
6. Метрики и логи: число повторов, число сообщений в DLQ, число отброшенных дубликатов (в дополнение к [metrics.md](metrics.md)).
7. Обновление `docs/architecture.md`: пункты 3, 4, 6, 8 переносятся из «Известных ограничений» в описание решения.

## Не в скоупе

- Transactional outbox и атомарность «запись в БД + публикация в Kafka» (п. 1 ограничений).
- Компенсация платежа и saga (п. 2).
- Идемпотентный ключ платежа в `payment` и промежуточный статус «оплачивается» (п. 5).
- Автоматический повторный разбор сообщений из DLQ (replay); разбор выполняется вручную.
- Дедупликация в `notification`: дубликат уведомления не меняет состояние системы.
- Асинхронная сборка вне consumer (п. 9, производительность).
- Миграция уже существующих сообщений в топиках.

## Технические ограничения

- Хранилище для дедупликации: Redis с TTL. Дубликаты, пришедшие позже TTL, не отсекаются.
- Redis должен быть доступен `assembly` и `order`; поведение при его недоступности нужно зафиксировать (см. критерии).
- Смена ключа сообщения меняет раскладку по партициям; события, уже лежащие в топиках с прежними ключами, порядок не получают.
- Дедупликация даёт семантику at-least-once + идемпотентная обработка, а не exactly-once: между обработкой и записью `event_uuid` остаётся окно, которое должно быть описано в документации.
- Значения по умолчанию (настраиваемые через конфиг): 3 повтора, backoff 1 с / 2 с / 4 с, TTL ключей дедупликации 24 ч.
- Задержка повторов блокирует партицию, поэтому суммарное время повторов не должно превышать `max.poll.interval`.
- Общий код consumer лежит в `platform/pkg/kafka`, поэтому изменения затрагивают все сервисы, которые его используют.

## Критерии готовности

- [x] В обоих producer ключ сообщения равен `order_uuid`; unit-тест проверяет ключ отправленного сообщения.
- [x] Если обработчик возвращает ошибку, consumer вызывает его повторно до 3 раз с задержками 1/2/4 с; тест подтверждает число вызовов.
- [x] Если обработчик успешен на 2-й попытке, сообщение не попадает в DLQ, offset помечен.
- [x] После исчерпания повторов сообщение появляется в `<topic>.dlq` с заголовками исходных topic/partition/offset и ошибки, offset помечен, следующее сообщение партиции обработано.
- [x] Если отправка в DLQ тоже не удалась, offset не помечается и сообщение обрабатывается заново.
- [x] Повторная доставка `order.paid` с тем же `event_uuid` не запускает сборку и не публикует второй `ship.assembled` (проверено тестом).
- [x] Повторная доставка `ship.assembled` с тем же `event_uuid` не вызывает повторного обновления заказа.
- [x] `UpdateOrderStatus` не меняет статус, если переход недопустим (например, `ASSEMBLED` -> `PAID`); тест покрывает все пары статусов.
- [x] Поведение при недоступности Redis определено, описано в `docs/architecture.md` и покрыто тестом.
- [x] Метрики повторов, DLQ и дубликатов экспортируются и описаны в `docs/metrics.md`.
- [x] Интеграционный тест (testcontainers или аналог): ошибка handler -> сообщение в DLQ, дубликат -> одна сборка.
- [x] `task test` и `task lint` проходят; покрытие изменённых пакетов не ниже текущего.
