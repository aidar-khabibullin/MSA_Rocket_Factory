# PRD: Envoy вместо самописного BFF

**Дата**: 2026-11-08
**Статус**: Draft

## Цель

Убрать самописный HTTP-шлюз `bff` (около 300 строк ручных хендлеров, маппинга ошибок и DTO) и отдать браузерному фронтенду единую точку входа на Envoy. Шлюз перестаёт быть кодом, который мы поддерживаем: перевод REST ↔ gRPC, маршрутизация и CORS описываются конфигурацией и аннотациями в proto.

## Пользовательские сценарии

- Пользователь регистрируется на фронтенде -> запрос `POST /api/auth/register` проходит через Envoy, `iam` создаёт пользователя, интерфейс показывает успех.
- Пользователь входит -> `POST /api/auth/login` возвращает сессию, фронтенд сохраняет её и запрашивает `GET /api/auth/me`.
- Пользователь открывает каталог -> `GET /api/parts` через Envoy попадает в `inventory`, список деталей отображается как сейчас.
- Пользователь создаёт, оплачивает и отменяет заказ -> запросы `/api/v1/...` через Envoy попадают в `order` по HTTP.
- Пользователь вводит неверный пароль или обращается без сессии -> фронтенд получает понятное сообщение и корректный HTTP-статус (400, 401, 404, 409), `401` по-прежнему приводит к выходу из сессии.
- Разработчик запускает `task web` -> фронтенд работает через Envoy без отдельного процесса BFF.
- Читатель открывает `docs/logo.png` -> на схеме на месте BFF стоит Envoy.

## В скоупе

- Сервис Envoy в `deploy/compose` с конфигурацией: gRPC-JSON transcoder для `iam` и `inventory`, маршрут `/api/v1` в `order`, CORS для origin фронтенда.
- Аннотации `google.api.http` в proto `iam` и `inventory` для методов, которые нужны фронтенду: `Register`, `Login`, `Whoami`, `ListParts`. Прежние пути сохраняются: `/api/auth/register`, `/api/auth/login`, `/api/auth/me`, `/api/parts`.
- Перегенерация кода из proto и дескриптора для Envoy (через существующие задачи `buf`/Taskfile).
- Передача сессии из заголовка запроса в gRPC-metadata `session-uuid`, которую читают `iam` и `inventory`.
- Передача адреса клиента в `x-forwarded-for`, по которому ограничитель попыток входа в `iam` считает попытки.
- Правки фронтенда: DTO и адаптеры в `frontend/src/modules/*/repository/` под формат proto-JSON (`int64` строкой, вложенные сообщения, вложенное тело регистрации), прокси Vite на один адрес.
- Удаление индикатора состояния сервисов: модуль `frontend/src/modules/system`, его использование в `layout.tsx`, ключи i18n и тесты; эндпоинт `/api/health`.
- Удаление `bff/` из репозитория и `go.work`, задачи `bff:run` из Taskfile, упоминаний BFF в README, `docs/architecture.md` и `frontend/AGENTS.md`.
- Обновление схемы `docs/logo.png`: Envoy вместо BFF.

## Не в скоупе

- Аутентификация на уровне Envoy (JWT-фильтр, внешняя авторизация): сессию по-прежнему проверяют `iam` и `inventory`.
- TLS, rate limiting и другие политики Envoy сверх перечисленного.
- Перевод `order` на gRPC или изменение его OpenAPI-контракта.
- Новые методы API для фронтенда сверх тех, что уже использует BFF.
- Агрегированный индикатор состояния сервисов в любом виде (ни в Envoy, ни отдельным сервисом).
- Изменение бизнес-логики и gRPC-контрактов сервисов (добавляются только HTTP-аннотации; единственное исключение — чтение сессии `Whoami` из metadata, см. ограничения).

## Технические ограничения

- Envoy transcoder отдаёт proto-JSON: `int64` приходит строкой, сообщения вложенные, поля по умолчанию в `lowerCamelCase`. Фронтенд ожидает `snake_case`, поэтому формат имён полей нужно зафиксировать явно, а расхождения закрыть в адаптерах (`*.dto.ts`, `*.adapter.ts`), как требует `frontend/AGENTS.md`: формат бэкенда живёт только в `repository/`.
- Метод `ListParts` принимает фильтр; через `GET` фильтр передаётся параметрами запроса, а пустой фильтр должен вести себя как сейчас.
- `iam` и `inventory` читают сессию из metadata `session-uuid` (`backend/platform/pkg/middleware/grpc`), а браузер шлёт заголовок `X-Session-Uuid`. Имя заголовка и имя metadata должны быть согласованы: фронтенд переходит на заголовок `Session-Uuid`.
- Envoy transcoder не умеет переносить заголовок в поле запроса. `Whoami` брал сессию из поля `session_uuid`, поэтому в `iam` добавлен обратно совместимый запасной путь: пустое поле заменяется значением metadata `session-uuid`. Это единственное изменение кода сервисов, остальное сводится к аннотациям.
- Ограничитель попыток входа в `iam` доверяет только `x-forwarded-for`, который выставляет шлюз. Envoy должен подставлять реальный адрес клиента, а не принимать заголовок от клиента как есть.
- Ошибки gRPC превращаются в HTTP-статусы и тело вида `{"code", "message", "details"}`. `extractMessage` во фронтенде уже читает поле `message`, и это поведение нельзя сломать.
- В dev браузер ходит только на origin Vite, прокси Vite решает CORS. CORS в Envoy нужен для запросов напрямую с `http://localhost:5173`.
- Изменения в `shared/proto` затрагивают все сервисы, использующие сгенерированный код: после правки должны проходить `task lint` и `task test`.

## Критерии готовности

- [ ] В `deploy/compose` есть сервис Envoy, поднимается командой `task up-all` вместе с остальными сервисами и проходит healthcheck.
- [ ] `POST /api/auth/register`, `POST /api/auth/login`, `GET /api/auth/me` и `GET /api/parts` через Envoy возвращают те же данные, что раньше через BFF, и работают с сессией из заголовка.
- [ ] Запросы `/api/v1/orders...` через Envoy доходят до `order` и работают так же, как при прямом обращении.
- [ ] Ошибки `400`, `401`, `404`, `409` приходят с корректным статусом, фронтенд показывает `message` из тела; ответ `401` приводит к выходу из сессии.
- [ ] Preflight `OPTIONS` с origin `http://localhost:5173` получает ответ с разрешением методов и заголовков `Content-Type` и заголовка сессии.
- [ ] `iam` получает в `x-forwarded-for` адрес клиента, а не адрес контейнера Envoy; заголовок, присланный клиентом, не принимается на веру.
- [ ] Пути `/api/auth/*` и `/api/parts` не изменились, `vite.config.ts` проксирует все `/api` на один адрес.
- [ ] Модуль `system`, его i18n-ключи, тесты и `/api/health` удалены; в интерфейсе нет ссылок на индикатор состояния.
- [ ] Каталог `bff/` удалён, `go.work` и Taskfile не ссылаются на него, задача `task web` запускает только фронтенд (Envoy поднимается стеком).
- [ ] Адаптеры и DTO фронтенда покрыты unit-тестами на `int64`-строки и вложенные тела; `task frontend:check` (типы, линтер, тесты) проходит.
- [ ] `task lint` и `task test` проходят для Go-модулей после перегенерации proto.
- [ ] CI на ветке зелёный.
- [ ] В `README.md`, `docs/architecture.md` и `frontend/AGENTS.md` BFF не упоминается, описан Envoy.
- [ ] `docs/logo.png` обновлён: на схеме Envoy вместо BFF (с логотипом Envoy), стрелки к `iam` и `inventory` идут от него, прямой путь фронтенда к `order` показан через Envoy.
