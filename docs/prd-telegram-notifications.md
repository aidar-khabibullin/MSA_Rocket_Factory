# PRD: Уведомления в Telegram (notification)

**Дата**: 2026-11-08
**Статус**: Implemented

## Цель

Сообщать пользователю в Telegram об оплате заказа и о готовности ракеты, не добавляя зависимостей в `order` и `assembly`.

## Пользовательские сценарии

- Заказ оплачен (`order.paid`) -> пользователь получает сообщение с ID заказа, способом оплаты и номером транзакции.
- Ракета собрана (`ship.assembled`) -> пользователь получает сообщение с ID заказа и временем сборки.
- У пользователя не настроен Telegram -> уведомление не отправляется, причина попадает в лог.

## В скоупе

- Consumer'ы `order.paid` и `ship.assembled` в группе `notification-service`.
- Получение Telegram `chat_id` пользователя через gRPC-клиент к `iam` (`GetUser`, способы оповещения).
- Telegram-клиент: отправка сообщения в чат.
- Тексты сообщений на русском: «Заказ оплачен», «Корабль собран».
- Структурированные логи успеха и ошибок.

## Не в скоупе

- Другие каналы (email, SMS, push).
- Настройка способов оповещения пользователем через API.
- Шаблоны и локализация сообщений.
- Дедупликация: повторное событие даёт повторное сообщение.

## Технические ограничения

- Токен бота и параметры Telegram задаются через окружение; в проекте есть переменная пропуска проверки Telegram для тестов и CI.
- Ошибка отправки возвращается из обработчика; повторы определяются общим consumer'ом (см. [prd-kafka-platform-messaging.md](prd-kafka-platform-messaging.md)).

## Критерии готовности

- [x] На `order.paid` отправляется сообщение с ID заказа, способом оплаты и транзакцией.
- [x] На `ship.assembled` отправляется сообщение с ID заказа и временем сборки.
- [x] Если Telegram-метод не найден, возвращается ошибка `telegram notification method not found`.
- [x] Unit-тесты сервиса, consumer'ов и декодеров.
- [x] Ограничение повторных уведомлений по одному `event_uuid`.
